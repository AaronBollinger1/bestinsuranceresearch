# Applying the redirects

The plan is generated by `scripts/plan-redirects.mjs` into `redirect-plan.json`. This file is the
runbook for turning that plan into live URL forwards, and the reason it is a runbook rather than a
script.

## Why this is not a single script that just does it

Porkbun's URL-forward write is not idempotent in a useful way: creating a second forward on the
same subdomain does not replace the first, and there is no update. So the correct operation per
domain is **list, delete what is there, create the new one** — three calls, in that order, with a
read in between. A script that skipped the delete would leave two forwards on one apex and the
behaviour would depend on which one Porkbun evaluated first.

More importantly, every one of these is permanent by design on a domain that in eight cases serves
a live site. That is not a thing to fire in a loop without reading the output.

## Preconditions

All four must hold. `scripts/plan-redirects.mjs` checks the first and will not mark the plan
`executable` without it.

1. **`bestinsuranceresearch.com` serves the built site.** Not registered, not resolving — serving.
   The preflight fetches `/position` and `/` and looks for markers only the real site emits,
   because a freshly registered Porkbun domain resolves immediately to a placeholder.
2. **The launch gate is cleared** for the destination, or you accept sending traffic to pages
   marked `under-review`.
3. **Deep-page mapping decided** for the eight live sites. An apex forward carries `/` only.
4. **Porkbun API access is on** for each domain being changed. Only `bestepli.com` and
   `bestinsuranceresearch.com` had it as of 2026-09-02; the rest is a per-domain toggle in the
   Porkbun UI.

## Order

Do the twenty-seven content-less domains first. They carry no traffic and no funnel, so they are
where you find out whether the destination behaves, at no cost. Only then the eight live sites,
one at a time, checking each before moving on.

## Per domain

For each operation in `redirect-plan.json`:

1. **Read what is there.**
   `list_url_forwards({ domain })`
   A freshly registered or parked Porkbun domain usually carries one 302 to
   `<domain>-com.l.ink` with `includePath: yes`. Note its `id`.

2. **Delete it.**
   `delete_url_forward({ domain, record_id })`
   Skip only if the list came back empty.

3. **Create the apex forward.**
   ```
   create_url_forward({
     domain,
     subdomain: '',
     location: '<the operation location from the plan>',
     type: 'permanent',        // 301
     includePath: 'no',
     wildcard: 'yes',
   })
   ```
   `includePath: 'no'` is deliberate. With `yes`, a request for
   `/class-codes/8810` on bestworkerscompensation.com would be sent to
   `/tools/workers-comp-classification/class-codes/8810`, which does not exist. Deep pages need
   per-URL mapping; a path-appending wildcard manufactures 404s at scale.

4. **Create the `www` forward.** Same call with `subdomain: 'www'`. Porkbun treats apex and `www`
   separately, and a domain whose `www` still points at parking will serve two different things.

5. **Verify before moving on.**
   ```bash
   curl -sI https://<domain>/        | head -5
   curl -sI https://www.<domain>/    | head -5
   ```
   You want a single `301` and a `Location` that is exactly the plan's target. Two hops means
   something else is still in the path — usually a leftover forward or a DNS record.

6. **Also check the DNS side on any domain that was on Vercel.** Deleting a URL forward does not
   remove an `A` or `CNAME` record pointing at a host. If the domain still resolves to Vercel, the
   forward may never be consulted. Use `list_dns_records({ domain })` and remove the records that
   pointed at the old deployment.

## Rollback

A 301 is cached aggressively by browsers and by crawlers, so rollback is slow rather than clean.
Deleting the forward and restoring the previous DNS returns the origin immediately, but clients
that cached the 301 will keep following it for as long as they cached it. That asymmetry is the
reason the order above starts with the domains that carry nothing.

## What not to do

- Do not point anything at the destination before it serves the site. A 301 to a parking page
  teaches a crawler that the destination is a parking page.
- Do not use `includePath: 'yes'` as a shortcut for deep pages. It produces plausible-looking URLs
  that 404.
- Do not batch the eight live sites. Each has its own funnel and its own indexed depth, and the
  point of going one at a time is to notice if the first one goes wrong.
- Do not remove the `MX` records or the SPF `TXT` while cleaning up DNS. They are unrelated to the
  site and removing them breaks mail forwarding.
